| 3.7-01 | P1 | style.css:215 (state: presenting) | In present mode the explore panel is hidden with `opacity: 0; pointer-events: none` only, so every panel control (ward/metric/LOS buttons, year sliders, switches, table rows) stays in the keyboard tab order while invisible. A keyboard user who enters Present and presses Tab cycles through dozens of invisible controls before reaching `#present-progress` / `#present-controls`. The stub pass cannot see this (it presses keys, never Tabs through the document). | §12 "Every control reachable by keyboard, visible focus ring"; WCAG 2.4.3 / 2.4.7. Fix: `.layout.presenting .panel { visibility: hidden; }` or set `inert` on `#panel` in onEnterPresent/onExitPresent. | 2.1 (lead, app.js/layout wiring) + 1.6 (style.css panel section) |
| 3.7-02 | P1 | ui/tour.js:137-143 + keyAction (tour.js:24-34) | The document-level keydown handler maps Space to `next` for any target that is not input/select/textarea. Buttons are not excluded: with focus on `#present-prev`, pressing **Space dispatches "next"** (the wrong direction); with focus on `#present-exit`, Space advances a scene instead of exiting; Enter/Space on a focused progress segment never fires its goto click (the handler preventDefault-s keydown, which suppresses button activation). Native button activation is broken for every present-chrome button. | §5 keyboard table, §12; WCAG 2.1.1. Fix: return early when `e.target.closest("button, [role='tab']")` (let native activation work), or treat `tag === "button"` like `inField`. | 1.14 (ui/tour.js) |
| 3.7-03 | P1 | ui/present.js:193-197 (progress tablist) | The progress bar is a real `tablist` with roving tabindex (`seg.tabIndex = i === index ? 0 : -1`) but no arrow-key navigation, so only the current scene's segment is keyboard-reachable; the other 14 tabs can never receive focus. Combined with 3.7-02, progress segments are unreachable and inoperable by keyboard even though §5 makes them the jump-to-scene control. The tabs also carry no `aria-controls` to the caption card. | §12 "the progress bar is a tablist" + every control keyboard reachable; WAI-ARIA tabs pattern. Fix: arrow/Home/End roving + activation on `#present-progress` emitting `{goto}`, `aria-controls="present-card"` per tab, and reconcile with the global arrow handler in tour.js (skip scene stepping when focus is in the tablist); or drop roving tabindex and make all segments tabbable. | 1.3 (ui/present.js) + 1.14 (ui/tour.js) |

Also the keyboard "wake" listener is on `#present` only, so a keyboard user whose focus is on the map or body cannot bring the controls back with a key. | §5 "auto hides after 3 s… any pointer movement or key brings it back". Fix: when hiding, remove the buttons from the tab order (`hidden` after the fade, `inert`, or tabindex -1) and drop `aria-hidden`; bind the keydown wake on `document`. | 1.3 (ui/present.js, present.css) |

Toggling autoplay with the **A** key (§5 keyboard table), or the reducer auto-disabling autoplay at the last scene (tour.js:14), leaves the switch showing off with `aria-checked="false"` while autoplay runs. role=switch misreports its state. | §5 "`Autoplay` as a switch", "A toggles autoplay"; WCAG 4.1.2.

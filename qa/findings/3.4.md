## Passes (verified against section 11)

- `collisions.geojson`: 1,206,286 B raw (1.15 MB) vs 1.6 MB budget; 62,757 B gzip (61 KB) vs 400 KB budget. PASS with ~25% / ~85% headroom.
- Total data: 1,639,528 B raw (1.56 MB: collisions + segments 250,836 + wards 104,895 + count_points 57,550 + summary 19,961) vs 2.2 MB budget. PASS.
- Console errors at 1440x900 and 1920x1080: none. PASS.

## Environment vs product

The harness relays every `api.mapbox.com` request through Node with a referer override because the token is localhost-blocked (`report.json.tileProbe.directStatus: 403`; origin emulation `https://clarksells.github.io/norman-traffic-dashboard/`). Two consequences: (1) every tile fetch carries relay latency, so load timings (`firstIdleMs`, `readyMs`) and all frame-time numbers that overlap tile churn are inflated relative to a direct 20 Mbps connection — the satellite-swap ~1.6–2.2 s max frame (3.4-03) is the documented example; (2) `bytesTransferred` of 23.4–32.3 MB per viewport is relayed Mapbox vector tile traffic re-downloaded per viewport with no shared cache — it is NOT the "total data under 2.2 MB" budget, which covers the app's own `data/*` files and passes comfortably. The only finding in this review that is clearly product rather than environment is 3.4-01 (`Style is not done loading` race). Everything frame- and load-time-related (3.4-02 through 3.4-05) needs one direct-connection or stubbed-tile verification run before it can be graded against the budget; the mobile scenes 3/4/12 medians of 16.7 ms show the harness itself is capable of registering budget-true frames.
